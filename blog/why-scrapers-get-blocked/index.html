Why your scraper gets blocked, and how to fix it

Vishnujan Narayanan · July 2026

Four layers block you: headers, TLS fingerprint, IP, behaviour. How to tell which one, and the fix for each.

A scraper gets blocked in four different ways, and from the outside they look almost identical. That is the whole difficulty: a fix aimed at the wrong layer does nothing at all, and the advice you find first — rotate your user agent, add some headers — only addresses one of the four.

Here is the case that makes the point. A stock-data site started answering a collection script with 405 Method Not Allowed. Nothing had changed on the client side. Headers could not have been the fix, because the site was not reading the headers: it was looking at the shape of the encrypted connection itself, which is decided before a single header is sent.

Below is each layer, how to tell from the outside that it is the one blocking you, and what actually clears it. Then the order to work through them in, cheapest first.

Before anything: make the block visible

When that 405 started, the run reported success. It fetched, caught the error, logged it where nobody was reading, and finished with zero new rows — which is exactly what a quiet day looks like. The data simply stopped growing.

Anything that can legitimately return nothing must be able to tell "the source had nothing" apart from "I was prevented from finding out." An explicit pass/fail count printed at the end of every run is the cheapest instrument in this whole post, and everything below is guesswork without it. Several of the failures in data ingestion bugs and how to catch them are the same shape.

Layer 1 — what you say: headers

Every HTTP request carries labels: which browser you claim to be, what you will accept back, which page you came from. This is where everyone starts and it is the least likely to be your problem — but getting it wrong blocks you on sites that block nothing else.

Data endpoints behind a public page are the clearest example. Many will not answer unless the request looks like it came from the page that normally calls them:

HEADERS = {
    "User-Agent": "Mozilla/5.0",
    "Accept": "application/json",
    "Referer": "https://www.nseindia.com/companies-listing/corporate-filings-insider-trading",
    "Accept-Language": "en-US,en;q=0.9",
}

The Referer is the load-bearing line: it says which page sent you. Many sites additionally require that you visited the ordinary page first, because that visit is what issues the cookie the data endpoint checks — so hold a session and fetch the human page once before the endpoint.

What does not help: rotating through a list of fake user agents. A site that checks headers checks whether they are coherent, not whether they are varied. ScrapeOps keeps a practical guide to complete header sets if you want a checklist for this layer.

The tell: the request fails identically every time, from every machine and network, including from curl, and adding the referer or the cookie fixes it immediately.

Layer 2 — how you connect: the TLS fingerprint

This is the layer that produced the 405, and the one most people have never heard of.

Before any HTTP request happens, your program and the server negotiate an encrypted connection. In that opening message your side lists which encryption methods it supports, in a particular order, with particular extensions. Python's networking library builds that list differently from Chrome, and the pattern is stable enough to be summarised as a fingerprint — JA3, now largely superseded by JA4. A bot-mitigation service compares it against what a real Chrome produces before it has read one byte of your request.

So a request claiming to be Chrome whose handshake is Python's is caught by a check that never looks at the claim. No header fixes this, and neither does trying harder in the same library. What fixes it is making the handshake match:

# curl_cffi impersonates a real browser's TLS/JA3 fingerprint, which is what
# gets past the site's Cloudflare bot mitigation (plain `requests` gets 405'd).
from curl_cffi import requests as cffi_requests

resp = cffi_requests.get(url, headers=HEADERS, impersonate="chrome131")

curl_cffi is a drop-in replacement for requests that speaks through a TLS stack configured to match a named browser version. One import and one argument; the rest of the script is unchanged. Outside Python, tls-client is the Go equivalent, and the same technique underlies most commercial "unblocker" products.

The tell: the same URL works in your browser, often works from curl, and fails from your script with a status unrelated to the request being malformed — 403, 405, or a challenge page. Getting a challenge while a real browser on the same machine and network sails through is the giveaway. The two-second check: fetch tls.browserleaks.com/json from your script, then open it in your browser, and compare the fingerprint fields. If they differ, this is your layer.

Layer 3 — where you connect from: the address

Once handshake and headers look right, the next thing a site has is your IP address. It knows two things about it: whether it belongs to a home connection or a data centre, and how it has behaved recently.

Sustained collection eventually hits Cloudflare's "confirm you are human" wall, served as ordinary-looking HTML with a 403, 405, 429 or 503 attached. Detecting it needs both signals, because the status alone is ambiguous and the page alone is just text:

BLOCK_STATUS = {403, 405, 429, 503}
CHALLENGE_MARKERS = ("cf-chl", "challenge-platform", "/cdn-cgi/challenge")

def looks_blocked(status_code, text=""):
    """True if a response is a Cloudflare block/challenge rather than real content."""
    return status_code in BLOCK_STATUS or any(m in text for m in CHALLENGE_MARKERS)

The response is rotation: a pool of addresses, a fixed number of requests through each before moving on, a fresh batch pulled and tested when the pool wears out. One working set of numbers: 10 requests per address, a 30-to-90-second pause between batches of 20, and every candidate address validated against the real site before it is trusted. Free proxy lists are mostly dead entries, so the validation pass is not optional.

Two caveats, because this is where advice gets irresponsible. Free proxies are unreliable, frequently slower than not scraping at all, and operated by people you do not know, which makes them unfit for anything carrying credentials. And rotation treats a symptom: if a site blocks your address after 200 requests, the cause is usually the rate rather than the identity, and pacing is the fix that keeps working when rotation stops.

There is a second shape of this worth knowing, because rotation cannot solve it. An app hosted on a cloud provider that fetches pages from a retailer on demand is blocked at every address it has, because the retailer scores data-centre ranges as a class. Rotating within a data centre does not help when the data centre is the thing being scored. The fix was to move the fetch to the one address the site had no reason to distrust — the visitor's own browser, which loads the page and hands the result back to the API. The trade-off is that the fetch now needs a client present, so it only works where the scraping happens in response to a user action. If your blocked scraper is user-triggered, this is the move nobody suggests and it costs nothing.

Layer 4 — whether you look like a person

Running a real browser clears the first two layers automatically and introduces a fourth: automated browsers announce themselves. The most famous signal is a property the browser sets when it is being driven by a program, readable in one line of JavaScript:

Object.defineProperty(navigator, 'webdriver', {get: () => undefined});
Object.defineProperty(navigator, 'languages', {get: () => ['en-US', 'en']});
Object.defineProperty(navigator, 'hardwareConcurrency', {get: () => 8});

There are dozens more — screen size, available fonts, how the browser renders a test image, whether a headless build reports the same graphics driver as a real one. playwright-stealth patches the known set, and undetected-chromedriver is the Selenium equivalent. Treat both as raising the bar rather than clearing it: this is an arms race between people publishing patches and people publishing new checks, and the checks are updated more often.

The other half of this layer is behaviour, and it is the half that decides. A real session has irregular gaps, does not request 400 pages at perfect 1.0-second intervals, and does not run at 03:00 for exactly the same duration every night. Jittered pauses and batch breaks cost almost nothing and remove the most obvious pattern you present.

Where a source checks hard, the answer is to stop hiding: run the browser visibly, log in once by hand, and save the session to a file so later runs start already authenticated. The mechanics of that are in Playwright vs Selenium.

Two failures that look like blocking and are not

Rate limiting. A 429 usually means slow down and clears on its own. It is not a verdict on you, and responding by rotating addresses converts a two-minute pause into a real block. It also has more than one meaning, which is its own post.

A cap you were never told about. Free tiers commonly truncate a response at a fixed row count — 200 is a popular one — with no error, no flag and no indication anything was withheld. A wide date window simply returns fewer records than it contains. Requesting one day at a time keeps every window under the cap. Nothing in the response will tell you; it is findable only by pulling the same range twice with different window sizes and noticing the totals disagree.

The order to work through it

Cheapest first, because each step rules out a layer:

1. Make the failure visible. Print how many requests succeeded and how many were refused.

2. Check whether you need the page at all. Open the browser's network tab and look for the endpoint the page itself calls. A JSON endpoint with the right Referer is less work to keep alive than a browser, and a smaller thing to be blocked for.

3. Fix the headers, once. Real user agent, correct Referer, visit the ordinary page first so you hold the cookie.

4. Match the handshake with curl_cffi or equivalent, if you get challenge pages a browser on the same machine does not.

5. Slow down before you rotate. Pacing fixes rate-based blocks permanently; rotation fixes them until the new address is scored too. Scrapy's AutoThrottle and Crawlee both do this adaptively, which beats any fixed delay you will pick by hand.

6. Use a real browser only when the content genuinely does not exist without JavaScript — and expect layer 4 once you do.

The part that is not technical

All of the above is about whether a request succeeds, which is a different question from whether it should be made. A defensible line: public data only, never anything behind a paywall or another person's login; honour robots.txt and the terms where they speak to this; keep the request rate low enough that nobody would notice the load; identify honestly where a site offers a way to. Every rate limit and pause described here exists for that reason too, not only to stay unblocked. If a site offers an API or a bulk download, that is the correct route even when it costs money — and it will outlive every technique in this post.

References and further reading

Cloudflare's own bot score documentation is the clearest description of these layers from the defending side: it names the signals, and it says plainly that the score is a learned combination of them rather than a rule you can satisfy.

Salesforce's JA3 repository explains how a handshake becomes a fingerprint in about a page, and JA4 is the current successor. Read one of them if layer 2 was new to you — it is the piece most scraping guides never mention.

Tools, by layer

  • curl_cffi (layer 2) — requests-compatible calls with a browser's TLS handshake. One import and an impersonate= argument.
  • browserleaks TLS probe (layer 2) — fetch it from your code and from your browser; if the fingerprints differ, that is your block.
  • tls-client (layer 2) — the same capability for Go.
  • Scrapy AutoThrottle and Crawlee (layer 3) — adaptive pacing, retries and proxy rotation, instead of hand-tuned delays.
  • playwright-stealth and undetected-chromedriver (layer 4) — the published patches for known automation signals. Both raise the bar rather than clearing it.
  • curl on HTTP cookies (layer 1) — worth reading when a site only answers after you have loaded an ordinary page first, which is a cookie problem wearing a blocking costume.

Rules, standards, and the legal side

  • RFC 9309 — the Robots Exclusion Protocol, standardised only in 2022, which is more recent than most people assume. Python's robotparser reads it in three lines.
  • MDN on 429 — being throttled versus being blocked, which decides whether to wait or to change something.
  • EFF on hiQ v. LinkedIn — the US appeals ruling that scraping publicly available data is not "unauthorised access" under the computer-crime statute. Context, not legal advice: it says nothing about contract terms, copyright, or other jurisdictions.
