Playwright vs Selenium: which to use and when

Vishnujan Narayanan · June 2026

Locators, saved sessions and pinned browsers — plus the 52 fixed sleeps that show what auto-waiting does not fix.

Both tools drive a real browser from code, and anything one can scrape the other can scrape. So the choice is not about capability. It is about how much code you write around the parts where a page is slower than your script, how a signed-in session is stored, and what happens when Chrome updates itself on the machine running your job at 3am.

Short version, if that is all you came for: new scraping work, use Playwright. An existing Selenium suite, leave it alone. Cross-browser testing on browsers you do not control, Selenium. And check first whether you need a browser at all — that last one saves more time than the choice does. The rest of this is why, with numbers from fourteen production scrapers that drive a browser, twelve on Playwright and two on Selenium.

What these tools actually do

A lot of a modern web page does not exist in the file the server sends. The server sends a mostly empty shell plus JavaScript, and the content appears a moment later. Fetch that page the plain way — the curl equivalent — and you get the shell. So instead you start an actual browser, usually invisibly, and tell it what to do: open this page, click that, now give me the text. Selenium (2004, and the reason the category exists) and Playwright (Microsoft, 2020) are two ways to issue those instructions.

Difference 1: waiting, and what auto-waiting really buys you

The core problem in browser automation is that your code runs instantly and a page does not. You ask for a button that has not been drawn yet and you get an error rather than a button.

Selenium's answer is that you say so explicitly — wrap what you want in a wait that polls until a condition holds:

self.wait = WebDriverWait(self.driver, 15)
news_tab = WebDriverWait(self.driver, 10).until(
    EC.element_to_be_clickable((By.XPATH, "//a[contains(text(),'News')]")))

The scraper that line comes from is 563 lines, and 12 of them are except clauses. One catches StaleElementReferenceException, which is the most Selenium-shaped failure there is and is worth understanding even if you never use Selenium: when you find an element, Selenium hands you a reference to that specific object in the page. If the page redraws that part of itself — which single-page sites do constantly, for reasons unrelated to you — your reference points at something that no longer exists, and using it raises. The element is still on screen. Your handle to it is not.

Playwright does not hand you the element. It hands you a locator: a stored description of how to find the element, resolved fresh every time you use it, waiting on its own.

await page.locator("input[name='password']").fill(PASSWORD)
await page.get_by_role("button", name="Log in").click()
await page.wait_for_url("**/home", timeout=15000)

Each line waits for the element to exist, be visible and be ready. There is no wait object, and a redraw between two lines is not an error, because the description is re-run rather than a handle reused. That is the real difference, and it is a difference in what you have to think about rather than in what is possible.

The part the marketing gets wrong

The usual claim is that auto-waiting means you stop writing sleep(5). Counted across those twelve Playwright scrapers: 52 calls to wait_for_timeout — a fixed sleep wearing a different name — against 25 uses of the proper "wait until this appears" call. Two out of three waits are still blind.

Separating why is the useful part, because one group is fine and the other is a smell:

Pacing. Many are deliberate — a pause between requests so the script reads more like a person and less like a flood. That has nothing to do with the tool and removing it would be a mistake.

No signal to wait on. Auto-waiting answers "is this element ready", which requires you to know which element proves the page is done. When clicking a filter triggers a background fetch that swaps the numbers inside cells already on screen, there is no new element to wait for. The correct fix is to wait for the network response by URL — page.expect_response(lambda r: "/api/quotes" in r.url) — and it is more work than a sleep, which is why sleeps win in more places than anyone would defend.

So the accurate claim is narrower than the popular one: auto-waiting removes the class of failure where the element was not there yet. It does not tell you when a page has finished, and it will not write that knowledge for you. If you take one technique from this section, take the network-response wait; it is the thing that actually deletes sleeps.

Difference 2: log in once, not every run

This changed how scripts get structured more than the waiting did, and it gets far less attention.

Signing in from code is the fragile part of any scraper: the login page is the most heavily defended on the site, and a wrong move costs you the account rather than the run. Playwright lets you sign in once, by hand, in a visible browser, then save what the browser learned — cookies and stored site data — to a JSON file:

browser = await p.chromium.launch(headless=False)   # visible: log in as a human
context = await browser.new_context()
# ... fill the login form once, then:
await context.storage_state(path="storageState.json")

Every later run starts from that file, already signed in, with no credentials in the scraping code at all. The Selenium equivalent is pointing Chrome at a saved user profile directory. It works and it is heavier: a whole browser profile on disk rather than a small file, carrying state you did not ask for, and two runs cannot share it simultaneously. Being able to commit a script with no password in it, and hand the session file over separately, is structural rather than a convenience — it is also what lets the same script run in CI without a secrets dance.

Difference 3: concurrency without a second service

Playwright's Python API has an async version, so one process can drive several pages at once. Selenium's route to concurrency is a browser per thread, which is much heavier and is why large Selenium setups end up wanting a Grid — a separate service that hands out browsers. If you would rather not write a pool at all, Crawlee wraps Playwright with request queueing, retries and concurrency limits already built.

Two cautions, both learned the expensive way. Parallel workers are where scraping bugs come from — the concurrency failures in data ingestion bugs and how to catch them were all caused by workers, not by sites. And running eight pages at once means arriving at a site eight times as fast, which is the quickest known method of turning a working scraper into a blocked one. Start at two or three.

Difference 4: the operational one, which nobody mentions until it breaks

Selenium drives a browser you supply, so the browser and its driver must be version-compatible — and Chrome updates itself roughly monthly. The traditional patch is webdriver-manager, which downloads a matching driver at runtime and adds a network call at startup where you did not previously have one. Since 4.6 Selenium ships Selenium Manager, which does the same job in-process and makes that dependency largely unnecessary. Worth knowing if you last touched Selenium before that, because it removes most of the version-matching pain this paragraph is about.

Playwright downloads and pins its own browser builds through playwright install. The browser is a dependency of the project rather than a property of the machine, so a script that ran last month runs the same way this month and the same way in a container. For unattended jobs on a schedule that is worth more than any API difference.

Where the choice makes no difference at all

Neither tool helps with the thing that actually stops scrapers, which is being refused. A stock-data site here started returning 405 to a plain Python request. It was not reading the code, the headers or the user agent. It was looking at the shape of the TLS handshake — the pattern of the encrypted connection itself, which differs between Python's networking library and a real Chrome. No browser-automation choice changes that. What fixed it was curl_cffi, which makes a plain HTTP request whose handshake matches Chrome's, with no browser at all:

# curl_cffi impersonates a real browser's TLS/JA3 fingerprint, which is what
# gets past the site's Cloudflare bot mitigation (plain `requests` gets 405'd).
from curl_cffi import requests as cffi_requests

Which leads to the biggest saving available here. A browser is the answer only when the data genuinely does not exist until JavaScript runs. Otherwise it is the most expensive tool on the shelf: starting Chrome to fetch a JSON endpoint costs hundreds of megabytes and about a second of startup to do what one HTTP request does in 200 milliseconds. Of the 32 collection scripts those fourteen browser scrapers belong to, 18 never open a browser at all. One of them is still named trendlyne_selenium.py and contains no Selenium whatsoever — it fetches HTML directly, and the filename is a fossil of the version that needed a browser for the same rows.

The check takes two minutes: open the network tab, reload the page, filter to XHR, and look at what the page itself is calling. If the numbers you want arrive in a JSON response, call that endpoint. It is faster, it breaks less often, and it is a smaller thing to get blocked for. When that fails, why your scraper gets blocked covers the four layers that decide whether you are allowed to.

How to choose

New scraping work: Playwright. Locators remove a class of error, sessions save to a file, browser versions are pinned, and concurrency needs no second service.

An existing Selenium suite: leave it. Nothing above justifies a rewrite, and a working scraper is worth more than a modern one. The two Selenium scripts here are the oldest files in the folder and still run; nothing was ported, only new work was written in the new tool.

Cross-browser testing across a fleet, or a team already running Grid: Selenium. It is a W3C standard with two decades of infrastructure behind it, which matters far more for a test suite that must run on browsers you do not control than for a scraper you run yourself.

Neither, if the page is not the point. Call the endpoint the page calls.

One limitation on all of this: it comes from porting the same jobs between the two tools over about two years, not from a controlled benchmark — no stopwatch, no same-site same-day comparison, so nothing here is a speed claim. The parts worth defending are the failure modes and the operations, because those have logs behind them.

References and further reading

Playwright's own page on actionability lists exactly which conditions each action waits for, which is the most useful page in either project's documentation and is the thing to read before deciding whether auto-waiting covers your case.

Selenium's waits documentation is direct about why implicit waits and explicit waits should not be mixed, which is a footgun I hit before I read it.

Documentation worth having open

  • Playwright — authentication: the save-the-session-to-a-file pattern from above, with more care about when a saved state expires.
  • Playwright — trace viewer: records a run and replays it with the DOM, network and console at every step. It is the single biggest debugging difference between the two tools and I did not use it for far too long.
  • Playwright — request interception: block images and fonts, or answer a request from your own data. Blocking media alone typically halves page-load time on a scrape.
  • Selenium Manager: the built-in driver resolution that replaced third-party driver managers from Selenium 4.6 onward.
  • Selenium BiDi: the bidirectional protocol that closes most of the capability gap — network interception and console access from Selenium, standardised rather than Chrome-only.
  • W3C WebDriver and the Chrome DevTools Protocol: the two wire protocols underneath all of this. Reading the second explains why Playwright can do things the first cannot express.

Tools mentioned

  • Crawlee for Python — queueing, retries, proxy rotation and concurrency around Playwright, so you are not rebuilding a crawler each time.
  • curl_cffi — HTTP requests whose TLS handshake matches a real browser, which is the fix when the page itself was never the problem.
  • undetected-chromedriver — the Selenium-side answer to automation detection, if you are staying on Selenium.
  • Scrapy — still the right tool when no JavaScript is involved: it is faster than any browser and its AutoThrottle handles pacing for you.
