How to make an ETL pipeline safe to rerun

Vishnujan Narayanan · July 2026

A rerun should repair data, not corrupt it. Four ways that rule breaks, and a six-point checklist.

A pipeline is safe to rerun when running it twice leaves the data no worse than running it once. Say it as a rule you can hold code to: a rerun must fill a gap, correct a bad row, or change nothing at all. Never duplicate, never delete, never move the finish line backwards.

That sounds like it should be the default and it is not. Below are the four ways the rule breaks in practice, the guard for each, and the one case that stays open. The examples come from scheduled scripts collecting market data, but every failure here belongs to any pipeline that runs on a timer against somebody else's system.

The design decision everything else follows from

The second run is the hard one. It has to decide what it already has and what it still needs, and there are only two places to get that answer from: a separate progress store, or the data itself.

Reading it from the data — find the newest row, ask the source for everything after that — is the better default for small and medium pipelines. There is no progress file to drift out of step with reality, because reality is the file. An interrupted run needs no cleanup: the next one reads what landed and carries on.

The price of that choice is one sentence, and it explains three of the four failures below:

Every row you write is an instruction to your future self. Write a bad row and you have not merely stored bad data, you have told the next run to start from the wrong place. Which means the checkpoint must be computed from validated rows, not from all rows — and "valid" has to be defined explicitly, per pipeline, in code.

Break 1: an empty row becomes the checkpoint

Many sources return a record all-or-nothing. Ask for a period that has not settled yet, or get quietly throttled, and you receive a row carrying a date and no values at all. Write it like any other row, then do this:

# Where do we continue from? The newest date in the file.
start = pd.read_csv(path)["Date"].max()

An empty row dated today is the newest date in the file. The pipeline concludes it is up to date, and every real period behind that empty row is never requested again. The gap is permanent, and it is the gap-filling logic that made it permanent.

The guard is one condition plus two policies. Continue from the newest row that actually carries a value:

# Continue only from rows that actually carry a closing price.
df = pd.read_csv(path)
start = df[df["Close"].notna()]["Date"].max()

Then: a response where every row is empty is a failed fetch, not data, so it never reaches the file. And a pass at startup deletes empty rows earlier runs already wrote, so old damage repairs itself rather than sitting there forever. Rows dated in the future get identical treatment — left alone, one of them convinces the pipeline it has data through 2027 and it stops fetching entirely.

Break 2: the storage location is derived from a network call

Per-item files named from a value looked up at runtime — a company name, a title, a slug — get a different name whenever that lookup degrades. Healthy source: the full name. Rate-limited: the bare identifier. Renamed upstream: a third answer.

Three answers means three files for one item. And because the pipeline works out what it has by reading the file, a new filename looks exactly like an item with no history, so it downloads the entire archive again into it. The end state is one item spread across three files, each holding a different partial copy, none complete.

The guard: resolve the path from the stable identifier only. In practice that means looking for an existing file for that identifier and reusing whatever it is already called — the name is decided once and then remembered, never recalculated. Then add a startup pass that merges duplicates already on disk into one file, keeping the union of rows and preferring the copy with real values where two disagree.

Stated generally: anything you derive from a network call will eventually come back different. If that value decides where data is stored, one bad minute at the source permanently splits your dataset.

Break 3: the duplicate check that creates duplicates

Rerunning deliberately re-reads a few periods you already have, because data arrives late and a run starting exactly where the last one stopped steps over it. So the pipeline constantly sees rows it already holds, and needs a reliable way to recognise them.

The usual approach is a key built from a few fields that together identify a row, discarding rows whose key you already hold. Implement that check as a merge — joining new rows against stored rows to see which match — and it works right up until the stored data itself contains duplicates. Then each new row matches several stored rows and you get one output row per match. The check meant to remove duplicates multiplies them.

The guard: ask the simpler question. Build the set of keys already stored, keep only new rows whose key is not in it. This is an anti-join, and it cannot inflate anything because it never joins:

def deduplicate(new_df, existing_df):
    new_keys = _composite_key(new_df, DEDUP_KEYS)
    existing_keys = set(_composite_key(existing_df, DEDUP_KEYS))
    return new_df[(~new_keys.isin(existing_keys)).values]

Two things underneath it matter as much as the anti-join.

The key must be built from fields that exist. Name three columns that are not in the response and every row gets the same empty key, which collapses entire days of records into one row with no error anywhere. Assert the columns exist before you build the key. If you would rather stay with DataFrame.merge, validate="one_to_one" raises on the inflation case instead of performing it quietly.

The same row must always produce the same key. It will not, by default. The same quantity arrives as 629221 one time and 629221.0 the next; the same date as 15-Jan-2026 here and 2026-01-15 there. Compared as text those differ, so the same row is stored twice. Force every field into one canonical form before the key is built — dates to a single format, anything numeric to an actual number. If your store is a database rather than files, this is what INSERT ... ON CONFLICT DO NOTHING against a unique constraint gives you for free, and it is the better answer when it is available.

Break 4: going too fast, and writing the wreckage

All of the above assumes the source keeps answering properly. Hit a rate limit and you often do not get a clean refusal — you get a partial or empty response, which is precisely how bad rows enter the file in the first place. Backing off is not politeness, it is a data-quality control.

A fixed delay is the wrong instrument: too slow on a good day, too aggressive on a bad one. An adaptive pool finds the source's tolerance by itself. Start with five requests in flight, drop one whenever the source returns an error, add one back after fifteen consecutive successes. Individual requests get three attempts with a widening wait and a hard ten-second cut-off.

Which refusals are worth retrying at all is its own question, since a limit that clears in three seconds and a quota that is finished for the month arrive as the same status code — that is unpicked in what a 429 really means.

The checklist

Everything above compresses into six things to put in a scheduled pipeline before you trust it:

  • Compute the checkpoint from validated rows only, and define "valid" explicitly.
  • Treat an all-empty response as a failed fetch, never as data.
  • Repair on startup — purge empty and future-dated rows, merge duplicate files. Old damage should heal, not accumulate.
  • Overlap on purpose. Resume from a buffer behind the checkpoint, not from the checkpoint, so late-arriving records are picked up.
  • Deduplicate with an anti-join on a normalised key whose columns you have asserted exist.
  • Write atomically. Temporary file, then rename over the original — the one filesystem operation that either happens or does not. A crash mid-write otherwise leaves a truncated file that the next run reads as the complete dataset.

The case this design cannot handle

All of it makes reruns recover from your mistakes. None of it helps when the source changes a value it already gave you.

If a record is corrected upstream, the duplicate check sees a key it already holds, decides it has that record, and throws the correction away. Converging on a stable dataset and accepting corrections pull in opposite directions, and using set membership picks one without ever really deciding to. For prices it mostly works out, since split adjustments get recalculated anyway; for filings and anything compliance-adjacent it is a genuine hole. The fix, when it matters, is to key on identity and store versions — the pattern a dbt snapshot implements — so a changed value becomes a new row rather than a discarded one.

The gap still open is telling "the source had nothing new" apart from "the source refused to answer", because both produce zero rows and look identical in the output. The likely fix for both problems is the same: re-download data you already have, on a schedule, and diff it against what you stored. The full accounting of what has broken across these pipelines, and the guards that came out of it, is in data ingestion bugs and how to catch them.

References and further reading

Jepsen tests databases by deliberately breaking them and then checking whether the data survived. The reports are worth reading even if you never touch distributed systems, because they are the clearest demonstration of the pattern behind this whole post: a system reporting success while quietly losing or duplicating writes.

If you are building this on a scheduler rather than by hand, Airflow's best practices state the same rule as a requirement: every task must be idempotent and re-runnable for its data interval. Its run and backfill model is the vocabulary for the windowing described above.

Doing each piece properly

  • Postgres INSERT ... ON CONFLICT — an upsert against a unique key is the database's version of the anti-join here, and it cannot inflate rows the way a careless merge can.
  • dbt incremental models — the same "only process what is new, and be safe to run twice" problem, with an explicit unique key and a full-refresh escape hatch.
  • dbt snapshots — what to do when the source rewrites its own history, which is the case my resume logic still cannot see.
  • Stripe idempotency keys — the clearest short explanation of idempotency from the API side: how a client retries safely when it does not know whether the first attempt landed.
  • pandera — declare what a valid row looks like and reject a load that does not match. The tidy version of the hand-written validity checks above; I am not using it yet, and probably should be.
  • Ext4 and data loss and Files are hard — required reading if your checkpoint is a file, which mine is.
  • tenacity — retries and backoff you do not have to write, for the "going too fast" section.
