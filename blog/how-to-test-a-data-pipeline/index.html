How to test a data pipeline: what tests miss

Vishnujan Narayanan · August 2026

A green suite is evidence about your code, not your data. The cheap tests that catch what it misses.

A data pipeline can have a green test suite and be completely broken in production, and this is normal rather than unlucky. The tests check that each function does what its author intended. Almost every way a scheduled pipeline dies is somewhere else: in the seam between two components, in the difference between a developer's machine and a clean one, in a third party changing something, or in a configuration value nobody reads.

What follows is the set of cheap tests that do catch those, in the order worth adding them, with a real failure behind each one. None of it needs infrastructure — no staging cluster, no data quality platform. Most of it is a single extra run of something you already have.

The four failures a unit test cannot see

These come from one scheduled pipeline: it collects job advertisements, scores each one against a stored profile, and sends the good ones to a chat app with a tailored resume attached. Fetch, filter, score, notify — the same four stages as most collection pipelines. It had 92 unit tests, every external service mocked, and continuous integration on every push. All four failures below were live for weeks. None of them was visible from the suite.

1. The error was caught, logged, and the run reported success

The function that sends a message read a threshold value to quote in the text:

threshold = settings.selection.apply_threshold

That setting lives under scoring: in the config file, not selection:. The config reader raises on a missing key deliberately, so typos fail loudly instead of silently returning nothing. It did fail loudly — into this, one level up in the orchestrator:

except Exception as exc:
    log.error("notification_error", job_id=job.job_id, error=str(exc))

Both decisions are right on their own. A config typo should raise. A failed notification should not roll back database writes that already committed. Together they convert a hard error into a line in a log file, and the run continues and finishes green.

What hid it completely was that a different function sends the end-of-run summary, and that one does not touch the mistyped setting. So summaries kept arriving on schedule and the channel looked alive. What never arrived was the per-match message — the entire product.

This is the single most common shape of pipeline breakage: an exception handler that logs and continues, around the step that is the point of the run. The generalisation is not "catch fewer exceptions". It is that a run's exit status has to be computed from what it produced, not from whether it reached the end. Count the things you meant to do and the things you did, and fail the run when those disagree.

2. The suite had been red on the server for a month

Exactly one test was failing, on every push, going back five weeks:

FAILED tests/test_smoke.py::test_repo_layout
AssertionError: Missing scaffold paths:
    CHANGELOG.md  PRD.md  job_automation_architecture.md

Those documents had been made local-only and removed from version control. The test still asserted they exist. They do exist on the developer machine, so it passed there every time; a fresh checkout has never had them, so it failed on the server every time. And a suite that is always red is a suite nobody reads, which is how the first failure survived.

The fix was not to delete the assertion but to write the property that was actually meant:

def test_operator_docs_are_not_tracked_by_git() -> None:
    tracked = subprocess.run(
        ["git", "ls-files", "--", *operator_docs], capture_output=True, text=True
    ).stdout.split()
    assert not tracked

That version means the same thing in a fresh checkout as on a developer machine. The original depended on the environment, so it was not a check at all — it was a description of one laptop.

The technique is smaller than the lesson and worth stealing today: run your suite inside a fresh clone of your own repository. It reproduces exactly what CI sees and it costs ten seconds.

rm -rf /tmp/cicheck && git clone -q . /tmp/cicheck
cd /tmp/cicheck && pytest -q

The same class of problem — a test that quietly depends on the machine it runs on — is why Testcontainers exists. If a test needs a database, starting a real one in a container beats asserting that the one on your laptop happens to be configured correctly.

3. The vendor retired the model underneath it

A live run died on a call to a hosted language model:

404 This model models/gemini-2.5-flash is no longer available to new users.

No code had changed. The provider withdrew the model for projects not already using it. No test suite catches this, because every test of that code path mocks the vendor — which is correct practice, and also means those tests assert precisely nothing about whether the vendor still answers.

Two things help. If you want the mocks to at least stay faithful to what the vendor really sent, VCR.py records real responses once and replays them, so the fixture is a transcript rather than something you invented. And for the live check, one detail is worth knowing: the provider's own "list available models" call still returned that model at the moment every generation request was returning 404. Listing is not proof of callability. A startup check that lists models passes while the pipeline is dead. A startup check that makes one tiny real call does not.

4. One bad optional part discarded the whole output

A run scored a genuine match, selected it, rendered the document, and reported nothing:

notification_error: Inline keyboard button url
'.../resume/....pdf' is invalid: wrong http url

The chat platform rejects the entire message if any single button URL is unreachable from the internet. A base-URL setting still held its shipped placeholder. One unset value threw away the only output the pipeline exists to produce.

The guard that generalises is not "validate that setting". It is: when you assemble a result out of several optional parts, a bad part should cost you that part, not the whole. Filter the buttons to the ones with a usable URL and send the message with whatever survives. The same rule applies to a row with one unparseable column, an export with one unavailable section, a digest with one dead feed.

Before you compare anything, measure the noise floor

This is the test that has to come first, and it is the one most often skipped. It comes from a different pipeline — a collector that pulls news headlines for a set of crypto assets — and it applies to any pipeline whose source is a live service.

The question was whether running the collector with several workers in parallel corrupted results. So a parallel run was compared against a single-worker baseline:

workers   4   →  77.9s   IDENTICAL     ← baseline
workers  12   →  40.5s   IDENTICAL
workers  20   →  26.0s   DIFF -34/+36
workers  32   →  25.9s   DIFF -38/+40

The obvious reading is that concurrency is safe up to twelve workers. That inference does not hold, and the shape of the differences is what gives it away: 34 articles missing and 36 extra. A concurrency bug loses writes. It does not politely swap one article for another. Symmetric substitution looks like the source returning a different result set.

So the next step removed concurrency from the question entirely: run the collector sequentially, twice, over the same range.

SEQUENTIAL vs SEQUENTIAL   (12 assets, 26 weekly slices each)
asset     runA   runB  missing  extra
BTC       1982   1978       14     10
ETH        494    487       17     10
...
TOTAL     4390   4387       55     52     →  2.44% churn, no concurrency involved

Every asset differed. The source returns a different set of results for the same query minutes apart, at a rate of about 2.44%. The parallel runs above had diverged from baseline by 1.7% to 2.6% — less than two sequential runs differ from each other. Concurrency was exonerated, and the two "identical" verdicts were luck rather than proof.

The rule: before asserting that a change preserves correctness, measure how much the system varies when you change nothing. Without that number, "identical to baseline" carries no information and neither does "slightly different". It costs one extra run, and it decides whether any of your other comparisons mean anything at all. It also tells you what your assertions are allowed to be — which is the next section.

What to assert when exact equality is off the table

Once you know the source will not repeat itself, tests that compare output to a stored file are dead. What replaces them are properties that can still fail deterministically. Two groups cover most of it.

Unit tests for the parts that are pure logic. Ranking is deterministic and descending. Excluded categories stay excluded. The text-repair step is idempotent — running it twice changes nothing the second time. The output directory contains only expected files. Properties like "idempotent" and "always sorted" are where Hypothesis earns its keep: it generates the inputs, including the empty and duplicate-heavy ones nobody writes by hand.

Scenario tests that kill a run and check the next one repairs it. This is the property a scheduled pipeline actually rests on, and it is fully testable offline against a fake source. Each test kills a run a different way: budget exhausted mid-run, interrupt mid-item, a wall of 503s, process death with no cleanup, a partial run resumed with a different worker count, an item entering the universe late, an item dropping out. The assertions are about the dataset afterwards — no duplicate identifiers, no null timestamps, no malformed progress rows, existing files byte-identical where nothing should have changed.

In the collector above that came to 52 tests, thirty of the first kind and twenty-two of the second, all offline against a synthetic feed. One assertion in the second group does more work than the rest, and it is not obvious why until you try to break it:

expected_max = (len(fresh) * SLICES
                + sum(SLICES - n for n in partial_done.values())
                + len(complete) * 3)
assert f.requests_made <= expected_max, f"refetched too much: {f.requests_made}"

The test kills a run partway and checks the next one finishes. But a collector with no resume logic at all would also finish — by fetching everything again. Bounding the number of requests is what makes the test about resumption rather than about completion. Assert on the work done, not only on the end state. The same trick catches an "incremental" load that quietly rebuilds the table, and a cache that never hits.

Say what the suite still cannot see

A suite's gaps are part of what it means, and writing them down is what stops the green tick being read as a guarantee. For the one above: the feed is mocked, so real malformed XML, truncated responses and genuine connection resets are untested. Retry paths are exercised through a mock returning an error string, never a real timeout. The mock returns one article per slice, so nothing tests behaviour at the source's result cap — and a wider request window silently returning fewer articles is exactly the failure that cap produces. The 2.44% noise figure was measured once, on one range, from one address, and is then treated as a constant.

None of those are reasons not to ship. They are the list of things that only an end-to-end run against the real dependencies can tell you, which is why that run belongs in the schedule.

What to set up on a new pipeline, in order

1. Make "nothing happened" distinguishable from "nothing was allowed to happen." Zero new rows is both the normal outcome and the failure outcome, and that ambiguity is the single most common way breakage hides. An explicit attempted/succeeded/failed count at the end of every run costs nothing and turns silence into a signal.

2. One end-to-end run against the real dependencies with throwaway data, in the schedule rather than in the test suite. It is the only thing that would have caught the retired model, the placeholder URL and the mistyped config key — all three in a single run.

3. Assert on the output, not on the calls. A test that verifies a function was invoked with certain arguments passes happily while the message it produced is rejected by the platform.

4. Measure the noise floor before comparing anything to a baseline. One extra unchanged run, and every later comparison becomes interpretable.

5. Kill the run in every way it can die, and assert the next run repairs it. This is chaos engineering at the scale of one script, and it needs no infrastructure: a KeyboardInterrupt, a killed process, a wall of 503s and an exhausted budget cover most of it.

6. Run the suite in a fresh clone before trusting it. Ten seconds, and it is the difference between a check and a description of your own machine.

7. Add assertions to the data itself, not only to the code. Row counts within a range, no nulls in the key columns, values inside a known set, freshness. This is the part with mature tooling — Great Expectations, dbt tests and pandera all do it — and the cheapest of them is a schema declaration that refuses the bad row instead of writing it.

The failures above came from two of my own scheduled pipelines, one of which is public; the code for both the suite and the rewritten smoke test is linked below. A green suite is evidence about the code, not about the product — and the tests that see the difference are, all of them, an hour's work.

References and further reading

Hillel Wayne's metamorphic testing is the formal name for what the scenario tests above are doing: asserting a relationship between two runs when you cannot state the correct answer for either one, which is exactly the situation a non-deterministic source puts you in.

The OSDI paper Simple Testing Can Prevent Most Critical Failures is the one to read if you only read one. Its finding — that most catastrophic failures in distributed systems come from error-handling code that was never exercised — describes failure 1 above exactly: the handler ran, caught, logged, and continued.

Testing data, not just code

  • Great Expectations — the standard vocabulary for assertions that belong on data: row counts within a range, columns not null, values in a set. Worth borrowing even if you never adopt the framework.
  • dbt data tests — uniqueness, referential integrity, accepted values and freshness. Four checks that catch most silent breakage in a warehouse.
  • Dagster asset checks — the same idea attached to the pipeline itself, so a failing data quality check blocks the downstream step instead of being noticed later.
  • pandera — declare a dataframe's schema and constraints, and fail the load rather than writing the bad row. The lightest thing on this list to adopt.
  • Data Validation for Machine Learning (Google, SysML 2019) — how they generate and evolve a schema from the data itself, and how they treat a schema mismatch as an alert rather than a crash.

Testing the code around it

  • Hypothesis — property-based testing. State the property, let it find the input that breaks it.
  • VCR.py — record real HTTP responses once, replay them forever. Fixtures that came from the real source rather than from your imagination.
  • Testcontainers — a real Postgres or Redis per test run, which removes a whole class of "passes on my machine" failures.
  • pytest — specifically fixtures and tmp_path, which is what makes kill-and-resume scenarios cheap to write in the first place.
  • Principles of chaos engineering — the discipline the scenario tests borrow from, minus the infrastructure.
