How to scrape a site that paginates by date

Vishnujan Narayanan · August 2026

Find the undocumented window cap, resume from behind, and dedup on a key that cannot fail silently.

Public archives paginate by date constantly: give me a start date and an end date, and I will give you what falls between them. Regulatory filings, press releases, court records, transaction histories. Pulling twenty years out of one of those is a few hundred requests, a way to remember where you stopped, and — the part everyone underestimates — a way to notice when an answer came back short.

Because the defining property of these endpoints is that they will not tell you when they gave you less than you asked for. No error, no flag, no total count. A truncated response and a complete one are the same shape. Everything below follows from that.

The worked example is a stock exchange's insider-trading disclosure endpoint — when a company director buys or sells shares in their own company they must tell the exchange, and those disclosures are public — going back twenty years into one file that stays current. The recipe is the same for any date-windowed source.

Step 1: find the window size the hard way

The obvious first attempt is one request covering 2005 to today. It fails in three different ways depending on how wide you go, and only one of them is obvious.

A very wide range times out — loud, easy to notice, easy to handle. A merely wide range does something worse: it returns quickly, with a valid response, containing some of the data. If you are not comparing against something external, you cannot tell.

So do not retry harder. Never ask a question big enough to get truncated:

DEFAULT_CHUNK_DAYS = 180   # max span fetched per request when looping a wide range

def fetch_range(session, from_date, to_date, chunk_days, retries=3):
    """Fetch a wide date range by splitting it into chunk_days-sized windows."""
    start = from_date
    while start <= to_date:
        end = min(start + timedelta(days=chunk_days - 1), to_date)
        ...
        start = end + timedelta(days=1)

180 days is not documented anywhere. The only way to find a cap nobody publishes is to walk into it deliberately while you can still tell you have hit it: pick a period you can verify independently, request it in progressively wider windows, and watch where the count stops growing. Then back off from that width. At 180 days, twenty years is about forty requests instead of thousands.

Two tells for a cap you have not found yet, both worth hard-coding as alarms: a response whose row count is a suspiciously round number (200, 500, 1000) is truncated until proven otherwise, and a wider window returning fewer rows than a narrower one means you crossed the limit.

Step 2: resume from behind where you stopped

The first run pulls the full history. Every run after that should start from the newest record already stored — but back up a buffer of days first, rather than resuming exactly where it stopped.

That buffer is not defensive padding. It is a correctness requirement, because records arrive late: a transaction from last Tuesday might be disclosed next Monday. Resume exactly where you stopped and you step straight over it, permanently, because you will never ask about that date again. Size the buffer from the source's own lateness, not from a round number that feels safe.

Which means overlap is now normal, and every update re-reads records you already have. That makes the deduplication step load-bearing rather than a safety net — it runs on every single update, and when it is wrong the damage is immediate.

Step 3: get the deduplication key right, because it fails silently

Deduplication works by building a key out of the fields that together identify a record, then discarding rows whose key you already hold. There are three ways to get this wrong and none of them raises.

Naming columns that do not exist. A key written from memory rather than from an actual response:

# What was used. None of these are real column names.
DEDUP_KEYS = ['personName', 'acqQty', 'securityName']

# What the endpoint actually returns.
DEDUP_KEYS = ['symbol', 'intimDt', 'acqName', 'secAcq']

With the first version every row produces the same empty key. To the deduplicator, every filing for a company on a given day is the same filing repeated — so it keeps one and drops the rest. A company that disclosed four separate transactions in a day is stored as one. Nothing raises, because building a key from a missing column is not by itself a crash, and the row count still looks plausible because it is never compared to anything. Assert the key columns exist against the first response you get; it is one line and it converts this into a startup failure.

Implementing the check as a merge. Fixing the key above exposed a second bug underneath it: a merge against stored data that already contains duplicate keys does not remove duplicates, it multiplies them — each new row matches several stored rows and you get one output row per match. The pipeline went from silently deleting records to silently inventing them.

Use a set-membership test — an anti-join. Build the set of keys already stored, keep only the new rows whose key is not in it:

def deduplicate(new_df, existing_df):
    new_keys = _composite_key(new_df, DEDUP_KEYS)
    existing_keys = set(_composite_key(existing_df, DEDUP_KEYS))
    return new_df[(~new_keys.isin(existing_keys)).values]

It cannot inflate anything, because it never joins — it asks yes or no about each incoming row and nothing else. If you would rather stay with DataFrame.merge, validate="one_to_one" makes it raise on exactly the inflation case instead of performing it quietly.

Assuming a record arrives the same way twice. It does not. The same quantity comes back as 629221 from one place and 629221.0 from another; the same date as 15-Jan-2026 here and 2026-01-15 there. As text those are different values, so the same record gets a different key each time and is stored twice. Canonicalise every field before the key is built:

for k in dedup_keys:
    if k == 'intimDt':
        col = pd.to_datetime(df[k], errors='coerce').dt.strftime('%Y-%m-%d')
    else:
        # '100', 100 and 100.0 all collapse to one key;
        # names are not numeric, so they fall back to their text form.
        numeric = pd.to_numeric(df[k], errors='coerce').astype('float64')
        col = numeric.where(numeric.notna(), df[k]).astype(str)
    parts.append(col.fillna('').astype(str))
return parts[0].str.cat(parts[1:], sep='|')

This reads like housekeeping. It is what makes the next problem solvable at all.

Step 4: assume the archive is behind itself

Collecting history is the easy half. The harder problem is that an archive's searchable index usually lags its own publication — here, by roughly 30 to 60 days. For a twenty-year backfill that does not matter. For anything current it means the most recent two months of your dataset are permanently incomplete, and nothing in the response says so. The data looks finished because there is no marker for "still arriving".

Test for this before you design around it: pick a record you know exists, and ask the endpoint for the window containing it, weekly, until it appears. The gap between its stated date and the date it became searchable is your lag.

The only real fix is a second source that publishes sooner. Supplement the recent window from it, map its fields onto the primary source's layout, and merge. That merge is only safe because of the canonicalisation in step 3 — without it, the same record from two sources produces two different keys and you end up with a dataset duplicated everywhere the sources overlap, which is worse than having one source.

Step 5: expect the second source to fight back

Two blocks worth knowing about, because neither is obvious from the error.

HTTP 405 through Cloudflare, unaffected by header changes. Rotating the user agent did nothing because the block was not reading headers. It was fingerprinting the TLS handshake — how the encrypted connection is opened, which differs between a Python HTTP library and a real browser regardless of what the headers claim. curl_cffi opens the connection the way Chrome does and gets past it; the full stack of blocking layers is in why your scraper gets blocked.

The more expensive part of that failure was the reporting: a fully blocked run finished successfully with zero new rows, which is exactly what a genuinely quiet day looks like. An explicit pass/fail summary at the end of the run is what stops "blocked" and "nothing new" from ever looking identical again.

A 200-record cap per response, undocumented. Same silent shortfall as step 1, from a completely different system. Ask for a month over a busy period, get 200 records and no truncation flag. Fetching one day at a time solves it, because a single day almost never exceeds the cap. And one IP address will not survive a full historical crawl, so it runs through a rotating pool of proxies.

What to check before you trust the output

Every failure above has the same shape: the output was plausible, and nothing checked it. Three defences, in the order they pay off.

Check totals against something outside the pipeline. Count records for a handful of entities you can verify by hand, and compare against the source's own published figures. That would have caught the broken dedup key in a day rather than months. No amount of internal consistency would have — the pipeline was perfectly consistent with itself.

Treat "nothing new" as a claim that needs evidence. It is the correct answer often enough to be unremarkable and wrong often enough to be dangerous; it was the visible symptom of both the block and the row cap. Anything that can legitimately return nothing must be able to say whether it looked and found nothing, or never got to look.

Decide what happens when a record is corrected. If an entity amends a past disclosure, the key sees a record it already holds and drops the amendment. That is a side effect of set membership, not a decision, and for a compliance-adjacent dataset it is the gap that matters most.

The pipelines these examples come from are private market-data collectors; what transfers is the recipe. The wider list of what breaks in scheduled ingestion is in data ingestion bugs and how to catch them, and the guards that make repeat runs safe are in how to make an ETL pipeline safe to rerun.

References and further reading

SEBI's Prohibition of Insider Trading Regulations, 2015 (the original gazette notification, amended several times since) set out who has to disclose what and by when. Those deadlines are the reason the data arrives late rather than wrong, and reading them is what turned "the source is unreliable" into a schedule I could design around.

NSE's insider trading disclosures page shows the same records a human would see. It is the fastest way to check a single company by hand when you suspect your own pipeline is dropping rows — and doing that check is what surfaced the deduplication bug.

The techniques, generalised

  • Airflow DAG runs and backfills — the standard vocabulary for "process this window, then that one, and let a rerun repair a window that failed". Worth reading even if you never install it, because it names what a hand-rolled windowed backfill is doing.
  • dbt snapshots — the standard answer to a source that revises history, which is what a filing amended after publication is.
  • pandas merge — validate="one_to_one" raises on the join that turns deduplication into duplication.
  • Postgres ON CONFLICT — the deduplication problem solved by a unique constraint instead of by application code, which is what I would reach for building this again.
  • curl_cffi — the fix for the supplement source's TLS-level block, in one import.
  • Python robotparser and RFC 9309 — what a crawler is expected to respect, in three lines of code and one short standard.
