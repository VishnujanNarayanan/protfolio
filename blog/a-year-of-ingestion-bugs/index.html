Data ingestion bugs, and how to catch them

Vishnujan Narayanan · August 2026

Five ways ingestion breaks, with the guard for each. Eight of about 30 bugs threw no error at all.

Ingestion — the stage that gets data out of somebody else's system and into yours — fails in five ways, and only four of them tell you. The fifth writes wrong data into your store, reports success, and leaves no trace anywhere in the run.

Here is the distribution, from about 30 bugs fixed over a year across 32 scheduled scripts that collect Indian market data: prices, company announcements, insider filings, news. Eight of the 30 produced no error message of any kind. The script finished, the file got bigger, and what was in it was wrong. Nothing below is specific to finance — a pipeline pulling orders from a payments provider breaks in the same five ways.

The distribution by file is lopsided in a way that is worth knowing before you start: two scripts account for 16 of the 30, and both are the ones that maintain long-lived local state between runs — a resume point, a file of accumulated history. Scripts that fetch a thing and write a file barely appear. Bugs live in state, not in requests. If you are deciding where to spend review effort, spend it wherever a run's output becomes the next run's input.

Each category below gets the failure, why it is invisible or not, and the guard that catches it.

1. Silently wrong data — 8 bugs

Every one of these ran to completion and reported success. This is the category worth your attention; the other four mostly announce themselves.

A deduplication key with column names that do not exist

Deduplicating incoming rows on a composite key is standard. Write the key from memory instead of from an actual response and you get this:

# The key the pipeline used. None of these are real column
# names in the response, so every row got the same (missing)
# key and collapsed into one.
DEDUP_KEYS = ["personName", "acqQty", "securityName"]

# The columns the source really returns.
DEDUP_KEYS = ["acqName", "secAcq", "symbol", "date"]

Pandas does not complain in the way you need it to. The effect: every distinct record for a symbol on a given day collapsed into one row, so a company that filed four separate trades in a day came through as one. There is no error state to detect here. The pipeline discards real records for as long as the key is wrong.

The guard: assert your key columns exist before you use them — set(DEDUP_KEYS) <= set(df.columns) is one line and turns a silent bug into a crash. Better, derive the key from a schema you validated the response against, so a renamed upstream column fails the load rather than the dedup.

The deduplication that added rows

Fixing that key exposed a second bug underneath it. The dedup was implemented as a merge, and a merge against existing data that already contains duplicate keys does not deduplicate — it does a partial cartesian product and inflates the row count. So the pipeline dropped rows for a while, then added rows that never existed.

The guard: two of them. Use an anti-join — keep only the rows whose key is not already stored — because it does not care what is already in the file, which a merge very much does. And if you are using DataFrame.merge, pass validate="one_to_one", which raises on exactly this instead of quietly inflating. It is the single highest-value argument in that API and almost nobody passes it.

Empty rows that become the resume point

Many APIs return a record all-or-nothing. yfinance, for example, hands back a row with a date and no prices when it is throttling you, or when you ask for a bar that has not settled yet. Write those rows, then resume from the newest date in the file, and the pipeline does this:

# Before: any row can become the resume point, including one
# that carries a date and no values at all.
start = pd.read_csv(path)["Date"].max()

# After: only rows that actually carry a value count.
df = pd.read_csv(path)
start = df[df["Close"].notna()]["Date"].max()

With the first version a blank row becomes the high-water mark and every real record behind it is skipped permanently. The gap-repair logic is what makes the gap permanent.

The guard: resume from the newest valid row, with "valid" defined explicitly per pipeline, and treat an all-empty response as a failed fetch rather than as data. Purge existing blank rows at startup, because they are still in there from before you knew.

Filenames that depend on whether you were rate-limited

Naming per-item files from a value looked up at runtime — a company name, a title, a slug — means the name changes when the lookup fails and falls back, and again when the upstream value is renamed. Each new filename is an empty file as far as resume logic is concerned, so it re-downloads the entire history into it. The end state was symbols sitting in three files with three overlapping partial copies of the same series.

The guard: file names come from the stable identifier only, never from a looked-up label. Add a startup consolidation pass that merges any existing duplicates into one canonical file, taking the union of rows and preferring the copy with valid values — you will need it for the mess already on disk.

A blocked run that looks like a successful one

A site started returning Cloudflare 405s to plain requests. The step that fetched from it caught the failure, logged it where nobody was reading, and the run reported success with zero rows added. Zero new rows is also exactly what a quiet day looks like, so from the outside those are indistinguishable.

The guard: a pass/fail summary printed at the end of every run — attempted, succeeded, failed, per source. It is crude and it is the single highest-yield line of code in this whole post. For the block itself, curl_cffi with Chrome impersonation gets you a matching TLS fingerprint rather than just a matching user agent; the four layers a block can come from, and how to tell them apart, are in why your scraper gets blocked.

The silent result cap

Free tiers commonly cap a response at N rows. One source here caps at 200. Ask for a 30-day window over a busy period and you get 200 rows and no indication whatsoever that you were truncated — no error, no flag, no has_more. You have to already know that 200 is the cap.

The guard: if a response comes back at exactly the round number you suspect is the cap, treat it as truncated and split the window. Narrow windows cost more requests and are worth it; this pipeline now chunks one day at a time by default. This is the failure I would look for first in anybody else's scraper.

Future-dated rows

Sources occasionally hand back a record dated ahead of today. Left alone it poisons the resume point for that item forever — the pipeline believes it has data through 2027 and stops fetching. The guard: reject anything dated after now at ingest, in the same place you reject the blank rows.

2. The source fighting back — 9 bugs

The largest category by count and the least interesting, because every one of them announced itself: 403s from Scrapy until the user agent rotated and the request rate dropped; a browser that crashed until it ran headless; a social platform rate-limiting hard enough to need seven cycles of three-minute waits on a fresh page, twelve-minute waits mid-scroll, and per-handle re-authentication; Cloudflare twice; eventually a rotating proxy pool, because one address was never going to finish a full crawl.

The useful outcome is not any individual fix, it is the thing that made most of them stop happening: an adaptive worker pool. Start at five concurrent workers, drop one on any rate-limit or API error, add one back after fifteen consecutive clean calls. It finds the source's tolerance on its own and re-finds it when the source changes its mind. Scrapy's AutoThrottle is the same idea as a built-in setting and is the right default if you are already in Scrapy. The hand-rolled version is about twenty lines, and it is described with the rest of the rerun-safety design in how to make an ETL pipeline safe to rerun.

3. Crashes and timeouts — 5 bugs

Unhandled exceptions in thread workers that killed a whole run's progress, and a downloader with no timeout at all that hung indefinitely on a stalled connection. Two rules fix the category and neither is clever: every network call gets an explicit timeout (there is no useful default; without one a stalled TCP connection hangs until the OS gives up, which can be hours), and worker functions return a result object rather than raising into the pool, so one bad item cannot take the run with it. Three retries, a ten-second timeout, exponential backoff. These are the bugs you fix once and stop thinking about.

4. Environment and config — 5 bugs

Hardcoded output directories, three separate times, each discovered by running the pipeline somewhere other than the machine it was written on. A script that broke when scripts/ was renamed to Scripts/ — a bug that only exists on case-sensitive filesystems and therefore only appears on the server.

Individually dull; collectively a sixth of the total, a proportion you only see by counting. Every one has the same root cause: a value that belongs to the environment, written into the code instead of passed into it. Paths, credentials, base URLs and worker counts are arguments. The cheap test that catches all of them at once is running the thing in a fresh clone in a container.

5. Concurrency — 3 bugs

All three are one bug approached three times. Every worker thread appended its result to a shared file by reading it, concatenating, deduplicating and writing it back:

# Before: every worker reads, merges and rewrites the whole file.
with combined_file_lock:
    combined = pd.read_csv(combined_path)
    combined = pd.concat([combined, new_rows])
    combined = combined.drop_duplicates(["Date", "Symbol"], keep="last")
    combined.to_csv(combined_path, index=False)

# After: workers return frames, one writer commits once.
frames = [f.result().df for f in as_completed(futures)]
(pd.concat(frames)
   .drop_duplicates(["Date", "Symbol"], keep="last")
   .to_csv(combined_path, index=False))

The lock stopped two threads writing at the same instant, which is not the same as making this correct. Writing a file in place is not atomic: an interruption mid-write leaves a truncated file that the next thread reads as the complete dataset and writes back. The correct shape is to write a temporary file and rename it over the original, which is the one filesystem operation that either happens or does not.

The guard, stated generally: one writer. Workers produce values and return them; a single thread commits, once, atomically. Three passes in a day went into making the write safer without changing the fact that every worker was rewriting the whole file, which is a fair indicator of where the problem was.

The two habits that would have caught most of this

"Write more tests" is the conclusion everybody agrees with and nobody acts on, and it is not quite right anyway: a passing suite is evidence about the code, not about the data (that argument is its own post). Two narrower habits would have caught more.

An empty result and a blocked result are different, and the run has to say which one it got. Three of the eight silent bugs are really one bug: blocked by Cloudflare, truncated at 200 rows, or emptied by a broken dedup key — and in all three cases the output was "zero new rows", which is also what a quiet Tuesday looks like. Anything that can return nothing must distinguish "the source had nothing" from "I was prevented from finding out".

Do not let the data be its own checkpoint unless you validate it first. Resuming from the newest row in the file is a genuinely good pattern — an interrupted run needs no separate state store. But any bad row you write becomes the instruction for where to start next time, and two of the eight silent bugs are exactly that. If you would rather not hand-roll the validity check, pandera lets you declare the schema and column constraints and fail the load instead of writing the row, and Great Expectations has a ready-made vocabulary for the same checks.

What none of this gives you is a way to find silent bugs that are live right now. The only mechanism I know of that would is re-fetching data you already have on a schedule and diffing it against itself — which is the next thing worth building, and which I expect will find things I will not enjoy.

Caveats on the count

"About 30" is doing some work in that sentence, and the ways it is soft are worth stating.

  • Small bugs fixed while doing something else do not appear, so 30 is an undercount by an unknown amount.
  • The three concurrency entries are one bug got wrong twice. Counting those as one moves the totals around by a few.
  • Classification after the fact biases toward the story already in place. The silent-versus-loud split is stark enough to survive that, but a category boundary could easily move by two or three.
  • Most importantly, this counts bugs that were found. The whole argument is that a class of bug produces no signal, so the honest position is that nobody knows how many are in there now.

The scripts behind the numbers are a private market-data collection stack; the failure modes, the guards and the code above are the parts that transfer, and the dedup case is worked through in detail in how to scrape a site that paginates by date.

References and further reading

Ding Yuan et al., Simple Testing Can Prevent Most Critical Failures (OSDI '14), looked at catastrophic failures in Cassandra, HBase, HDFS, MapReduce and Redis and found the majority came from error-handling code that was wrong or empty rather than from the original error. Category 1 above is that paper, at one-person scale.

Jepsen's analyses are the best demonstration I know that a system will happily tell you everything is fine while losing your writes, and that the only way to know otherwise is to go looking on purpose. Different scale, same problem as the dedup key.

The specific fixes, in someone else's words

  • pandas merge — the validate="one_to_one" argument raises on the row-multiplying join that turned my deduplication into duplication.
  • pandas drop_duplicates — worth reading closely for what happens when a named subset column is missing, which is the mechanism behind the first silent bug.
  • Postgres INSERT ... ON CONFLICT — the same problem solved properly by a database. If your pipeline can write to Postgres instead of a CSV, most of category 1 stops being possible.
  • Ext4 and data loss (LWN) — why "write the file in place" is not safe, and why write-temp-then-rename is the pattern.
  • How SQLite implements atomic commit — the long version of the same idea, and a good argument for using a database rather than reimplementing one badly around a CSV.
  • pandera and Great Expectations — declare what a valid row looks like and fail the load, rather than discovering it downstream.
  • Airflow best practices — the idempotency and "tasks must be re-runnable" rules, which is the same discipline these scripts arrived at without a scheduler.
