Local model or hosted API is usually argued on speed and price. On a real task neither decided it. The deciding number was 45 — the number of documents a free hosted tier would process in a day before the quota closed.

Here is the shape of that arithmetic, because it is the calculation worth doing first. A free tier allowing 1,000 requests and 100,000 tokens a day sounds generous until you divide: at roughly 2,200 tokens per document, the token budget runs out at about 45 documents, not 1,000. Whichever limit is smallest is your real limit, and for anything text-heavy it is almost always tokens. If a single run reads 25 documents, two runs end the day.

So this is what moving that work onto a 6GB laptop GPU cost and bought, on the same extraction task: read a job advertisement and return title, seniority, years required, pay range and skills as structured fields. Four times the latency, no cap, and one measurement that looked like a success before it had measured the thing that mattered.

What decides which model you can run

A language model is a large file of numbers. To answer quickly, that file has to sit in the memory attached to the graphics card — VRAM — because that is the memory the chip doing the arithmetic can reach at speed. Anything that does not fit spills into ordinary system memory and answers at a fraction of the pace.

So the model you can run is decided almost entirely by VRAM. At the usual four-bit compression — quantisation, which stores each weight in four bits instead of sixteen, costing a little accuracy for about a quarter of the size — 6GB buys roughly:

  • 3–4 billion parameters — about 2.5GB. Comfortable, fastest.
  • 7–8 billion — about 4.7GB. The largest that makes sense on this card.
  • 13–14 billion — about 9GB. Spills, and slows accordingly.
  • 26 billion and up — about 17GB. Not viable.

Two ways people get this wrong. The first is sizing against system RAM: an environment reporting 7.6GB of RAM says nothing about what the GPU can hold, and raising it would not allow a larger model. VRAM caps model size; system RAM only matters for the layers that spill. The second is sizing against the parameter count instead of the file. Compare your VRAM against the actual download size listed on the model's page — that is the number that has to fit.

And even a nominal fit is not clean. During a real run at 7 billion parameters the server reports 5.1GB resident and an 18/82 split between CPU and GPU: a fifth of the work lands on the processor, because the model plus its context window does not quite fit. Budget for the context, not just the weights.

The comparison, same schema, same documents

  • Hosted, 70-billion-parameter model: 1.6 seconds per document.
  • Local, 7-billion-parameter model: about 6 seconds, plus 18 seconds the first time while the model loads into VRAM.

Roughly four times slower. For a 25-document run that is two and a half minutes against forty seconds, on a job that runs a few times a day and that nobody is waiting on. That is the trade in one line: four times the latency, and the cap disappears entirely.

The cap is not the only thing that goes. With no token budget, documents no longer have to be clipped to fit — and these average 4,400 characters, reach nearly 12,000, and mention pay a median of 77% of the way in. Clipping to survive a hosted budget was measurably discarding the part of the text the task most needed. That is worth checking on any pipeline that truncates inputs: measure where in the document your target information actually appears before you decide where to cut.

Nothing leaves the machine either, which matters more for a personal document than for a public job ad.

What this is not is a cost saving. The GPU is a laptop already owned, the electricity is not metered separately, and the hosted tier being hit is free. If you are choosing between a rented GPU and an API, that is a real calculation and this is not it — the case here is caps and privacy, not money.

The technique that makes a small model usable: constrain the output

A 7-billion model is not a 70-billion model, and the difference shows up first as malformed answers rather than wrong ones. A typical one: asked for employment type, it answers hybrid, which is an answer about location.

1 validation error for JDParsed
job_type
  Input should be 'fulltime', 'contract', 'internship' or 'parttime'
  [type=literal_error, input_value='hybrid']

The usual handling is to notice after the fact and ask again. Each re-ask is a whole new inference, so one call took 83 seconds across four attempts. Two fixes, and the difference between them is the part worth keeping.

Describing the fields better. "Employment type if stated" and "Work arrangement if stated" are genuinely easy to conflate. Rewriting each description to explicitly exclude the other took it from four re-asks to zero or one. Cheap, helps every model, and still only persuasion.

Making the wrong answer unproducible. A model generates one token at a time, choosing from everything it could say next. Constrained decoding narrows that choice to what the schema permits: after "job_type": ", the only continuations available are the four allowed values. hybrid is not rejected after the fact — it is never available. Ollama compiles a JSON schema into that constraint directly, the same idea underlies llama.cpp's grammars and OpenAI's structured outputs, so the technique transfers whichever side you land on.

With the schema enforced: five responses out of five validated, no re-asks, average call down to about six seconds. Which is where it is tempting to declare victory.

Why "it validates" is the wrong success metric

"Five out of five valid" measures conformance to a schema. It does not measure whether the answers contain anything.

Three of the fields — required skills, nice-to-haves, responsibilities — were optional lists. An absent key is valid. So a response naming not one skill from the document scored exactly as well as a complete one. Measured across real documents rather than one test case: the local model returned no required skills at all on 71% of them, while the hosted model populated them. Everything downstream depended on those skills, so the parses were passing validation and feeding an empty comparison.

Separating the causes took an ablation — twelve documents, two runs each, changing one thing at a time — and it found three independent permissions to skip the work:

  • The schema permitted it. The three list fields had defaults, so they were not in the schema's required set, and the grammar allowed the model to omit the keys entirely. They were absent, not empty — the empty lists visible downstream were manufactured by the model definition after the fact.
  • The system prompt licensed it — "when a field is not stated, return null or an empty list".
  • The user prompt never asked for them. Every scalar field had an explicit instruction; these three had none.

Fixing only the prompt moved the empty rate from 71% to 62%, while sharply improving whatever did come back. That split is the finding: the schema controls whether a field appears at all; the prompt controls how good it is. Both were needed. Schema plus a prompt naming the three fields and asking for exhaustive extraction took it to 0 empty out of 12.

So the check to write is not "did it parse". It is required_skills is present and non-empty on at least N% of a sample you look at by hand. Put a minItems in the schema where a field must not be empty, and measure content rates per field on every model change. Those are different tests and only the second one is about the model.

One more trap: measurements about someone else's software expire

An early measurement here concluded that the local server's OpenAI-compatible endpoint ignored schema enforcement, so a separate transport was written to speak to its native endpoint instead. Re-measured later against a current version with a direct probe, that endpoint does honour it, respecting both required fields and minimum list lengths. The original result was either confounded or accurate for a version that has since moved.

The measurement is not the interesting part — measurements go stale. The chain it started is: the conclusion went into a code comment, the comment justified keeping a second transport, and the second transport is where the missing-fields behaviour lived. A comment asserting something about a third party's behaviour should carry the date and the version it was taken against, so the next person knows whether to trust it or re-probe. The bespoke transport has been deleted.

How to choose

Hosted API when the task is hard, latency is user-facing, or volume is spiky and unpredictable. A 70-billion model on someone else's hardware reasons better than anything that fits in 6GB, and no amount of prompt work closes that.

Local when the task is narrow and repetitive — extract these fields from this document — when volume is steady and would collide with a daily cap, when nobody is waiting on the response, or when the text should not leave the machine.

Both, ordered by cost. The arrangement that has held up is a chain: local first because it is uncapped, then the free hosted tier, then a metered account reached only when everything free has failed. Ordering by cost only works if the failure that moves you down the chain is classified correctly, which is exactly the problem in what a 429 really means — it decides when to give up on one link and take the next.

If you take one thing: constrain the output with a schema, then measure whether the fields have content rather than whether they parse.
