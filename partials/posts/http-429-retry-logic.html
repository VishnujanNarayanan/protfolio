These two messages came from the same API, six hours apart, both as HTTP 429:

429 Rate limit reached ... on tokens per minute (TPM):
    Limit 12000, Used 10986. Please try again in 3.035s.

429 Your project has exceeded its monthly spending cap.

The first clears in three seconds. The second holds until somebody raises a limit or the month rolls over. A retry loop that treats them the same handles one of them badly, and which one depends on which way you guessed.

The status code cannot tell you which you got, because HTTP status codes say what went wrong and never how widely. The difference lives in the human-readable text. Here is how to sort them apart, what breaks when you do it naively, and the roughly forty lines that end up being correct.

The assumption inside a plain retry loop

Programs that call other people's services fail intermittently: a connection drops, a server is briefly busy. The standard response is to try again after a pause, doubling it each time — 2s, 4s, 8s, give up. Exponential backoff, near-free to write, and free outright from tenacity or urllib3's Retry:

except Exception as exc:
    if attempt < attempts:
        time.sleep(delay)
        delay = min(delay * 2, max_delay)

Written that way, the loop encodes a belief: every failure is worth waiting for. With batches of 25 items, five attempts each and the pause capped at 90 seconds, a provider retiring a model — every call returning 404 no longer available — turns a permanent failure into about four minutes of waiting per item, applied to all 25. The run does not crash. It produces identical errors for fifteen minutes and reports done.

So two classes, which is where most retry code ends up:

  • Transient — 503, timeouts, 429. Retry with backoff.
  • Permanent — 404 unknown model, 401 bad key, 400 malformed request. Fail immediately; the next attempt is identical to this one.

That is not enough, and 429 is exactly where it fails.

The third class: scope, not recoverability

A spend cap is not recoverable inside a run, but that is not the interesting part. The interesting part is that it says something about every subsequent call. A 404 on item 3 tells you nothing about item 4. A spend cap on item 3 tells you precisely what will happen to items 4 through 25.

So classify by scope:

  • Transient — scope: this call. Retry.
  • Permanent — scope: this call. Fail this item, continue the batch.
  • Exhausted — scope: the whole account. Stop the batch, or move to a different provider.

The question that assigns the class is always the same one: does this failure predict the next call's failure?

Where a RateLimit header is present, it gives you the limit, what is left and when the window resets as structured fields, with no English to pattern-match. Check for it first. It is still a draft standard, so treat it as a bonus rather than a plan, and be ready to read the prose.

Reading the prose, and the word that poisoned it

Two practical notes before the failure, because both are counterintuitive.

You cannot classify by exception type. Between an SDK, a structured-output wrapper and the transport underneath, one failure arrives as three nested classes wrapping each other. The status text is the one thing that survives every layer.

Vendors write error messages for humans, and sometimes for marketing. That is the trap. A list of "this account is exhausted" markers that includes the substring billing looks reasonable — spend-cap messages do mention billing. But some providers append an upsell to every rate-limit message they send:

429 Rate limit reached for model `llama-3.3-70b-versatile` on tokens per minute
(TPM): Limit 12000, Used 10986, Requested 1621. Please try again in 3.035s.
Need more tokens? Upgrade to Dev Tier today at https://console.groq.com/settings/billing

Routine throttling, clearing in three seconds, containing the word that meant "your account is finished". The classifier promoted it to exhaustion and the run moved to a fallback provider that was itself spend-capped. Two runs ended early that way, at 5 of 21 jobs and 4 of 13.

The taxonomy was not wrong. The evidence used to detect one of its classes was contaminated by text that had nothing to do with the error — an advertisement, not a description. The fix is to make classification ordered, so a narrow, specific signal outranks a broad, incidental one:

def _is_budget_exhausted(exc) -> bool:
    message = str(exc).casefold()
    if any(m in message for m in _DAILY_QUOTA_MARKERS):     # "tokens per day"
        return True
    if any(m in message for m in _TRANSIENT_RATE_MARKERS):  # "tokens per minute"
        return False
    return any(m in message for m in _BUDGET_ERROR_MARKERS)

billing came out of the markers, which opened a gap in the other direction — a genuine paywall, one provider returning 402 payment_required, then read as transient — so payment_required went in explicitly. The only thing that caught that was running four real, saved error messages through the classifier and printing what each came out as. Four strings, four expected answers, one test. Do this before you ship the classifier, not after.

The fourth axis: same words, two different clocks

The same provider expresses both of its limits with the same opening phrase:

... rate limit reached ... on tokens per minute (TPM): Limit 12000 ...
... rate limit reached ... on tokens per day   (TPD): Limit 100000, Used 98752 ...

Per-minute reopens inside the run. Per-day does not. So "exhausted" is not purely about scope — it is about whether the window reopens before you finish. A daily quota is exhaustion for this run's purposes even though it is worded identically to the case that clears in seconds. That is why the daily markers are checked first above: it is the narrowest available signal, and it outranks wording it shares with the transient case.

Honour the wait the provider states

Independently of classification, there is a second source of wasted attempts. Providers that throttle usually tell you exactly how long to wait:

Please try again in 11.344999999s

A loop that ignores that and backs off on its own schedule — 2s, 4s, 8s — arrives before the window has reopened every single time, is refused every time, and burns all five attempts. The limit would have cleared on its own in eleven seconds; the run instead spends its whole attempt budget arriving early and escalates to a fallback it did not need.

hinted = retry_after_seconds(exc)      # parsed out of the message
wait = hinted if hinted is not None else delay
time.sleep(wait)
if hinted is None:
    delay = min(delay * 2, max_delay)   # exponential only when guessing

Two details worth copying. Add a small margin — half a second — because retrying on the exact boundary is routinely a hair early. And cap what you will honour: a stated wait of an hour is a daily quota in disguise, so above 60 seconds ignore the hint and classify as exhaustion rather than blocking the run.

Where a header is available instead of a sentence, this is the same idea done properly: Retry-After is standard, defined in RFC 9110. Reading it beats guessing, because the server knows when its own window reopens and you do not. It accepts either a number of seconds or an HTTP date, so parse both.

"Should I stop?" needs "and", not "or"

One more shape, which appears as soon as there is more than one provider to fall back to. The obvious rule — if any provider reports exhaustion, abandon the batch — is satisfied by a briefly-throttled primary plus a spend-capped fallback, and it stopped a run at 4 of 13 jobs while the primary's window was seconds from reopening.

The question the rule is trying to ask is still will the next item fail the same way?, and it will only if every provider failed for a reason that persists. So the condition is "some account is exhausted and nobody merely ran out of patience":

any_transient = any(getattr(e, "transient", False) for _cfg, e in failures)
if budget_failures and not any_transient:
    raise LLMBudgetError(summary)   # nothing will serve; stop the batch
raise LLMError(summary)             # this item failed; the next may not

Requiring all failures to be budget errors is wrong in the other direction: a retired model on the primary plus a capped fallback would keep going item after item with nothing able to answer. Both mistakes are one word apart, which is the argument for writing the rule as an explicit statement about the list of failures rather than as flags accumulated inside a loop — and for a test that names both directions.

What to build on day one

Three classes, not two. Transient, permanent, exhausted — and decide the third by scope: does this failure predict the next call's failure?

Read the provider's stated wait before applying your own. Cap it, add a margin, and treat an implausibly long one as exhaustion.

Match on specific phrases, in order, narrowest first. Never on a word that could appear in marketing text. tokens per day is a signal; billing is a coincidence.

Keep the real error strings. A handful of saved messages from live failures is worth more than any reasoning about what providers ought to send, and they make the classifier testable in four lines.

Add a circuit breaker once there is more than one caller. The rules above decide what one batch does. When several jobs share an account, what stops them collectively hammering a struggling provider is a breaker that trips after N consecutive failures and stays open for a cool-down.

Log which class you assigned, every time. Every failure above was visible in hindsight only because the retry line recorded how long it waited and whether the figure came from the provider or from the backoff.

One limitation: this is calibrated against three providers used in my own scheduled jobs, and the marker lists are specific to how those three word things. The three classes generalise; the strings do not, and anyone copying this should expect to add their own after the first surprise.

References and further reading

Google's SRE book chapter on handling overload covers the other side of this: why a server sends 429 at all, and why clients retrying aggressively make a struggling service worse rather than better. Its companion chapter on cascading failures is the one to read if your retries are pointed at a service you own.

AWS's timeouts, retries and backoff with jitter is the clearest short explanation of why random jitter belongs in the pause — without it, everything that failed together retries together.

The specifications

  • RFC 6585 §4 — where 429 is defined. Worth reading for how little it says: too many requests, and explicitly not which limit was hit or for how long.
  • RFC 9110 — Retry-After — the header that removes the guesswork, in both its seconds and its date form.
  • RateLimit header fields (IETF draft) — limit, remaining and reset as structured fields. Check whether your provider already sends them before you write a parser for their prose.
  • Stripe — idempotency keys — the other half of retrying safely: how to retry a request that may already have succeeded without doing it twice.

Implementations you can copy instead of writing

  • tenacity — retry policies as decorators, including jitter and per-exception rules, which maps cleanly onto the three classes above.
  • urllib3 Retry — status-aware retries under requests, and it honours Retry-After if you set respect_retry_after_header.
  • Circuit breaker — the pattern for stopping calls entirely after repeated failures, which is what "exhausted" wants once more than one job shares an account.
  • Stripe on rate limiters — written from the server side, and the clearest explanation of why different limits exist and therefore why one status code has to cover all of them.
  • Groq's rate-limit documentation — a concrete example of per-minute and per-day quotas sitting behind the same status, which is the ambiguity the whole post is about.
